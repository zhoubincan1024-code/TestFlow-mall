## 1. 项目概述

### 1.1 项目背景与目标

本项目以开源电商系统 **macrozheng/mall 后台管理系统** 为被测对象，覆盖 **功能测试、接口自动化、UI 自动化、数据库一致性验证、性能测试与调优** 全链路，目标为 2026 软件测试校招打造一套完整的、可讲述的测试实战资产。

### 1.2 被测系统架构（本地部署）

```text
浏览器（Chrome）
    │  http://localhost:5173
    ▼
mall-admin-web（Vue3 管理后台前端，Hash 路由 #/xxx）
    │  API http://localhost:8080，请求头 Authorization: Bearer <JWT>
    ▼
mall-admin（Spring Boot 3.5 后端，接口无 /admin 前缀，如 /product/list、/order/list）
    ├── MySQL 8.0（库 mall，账号 mall/mall123456，native_password）
    └── Redis（localhost:6379，无密码）
```

### 3.1 M1 本地部署与验证

**目标**：将 mall 后端（Spring Boot）与 mall-admin-web 前端在本地跑通，建立被测环境基线。

**执行**：
- 编译打包后端 jar，启动 MySQL / Redis / 后端 / 前端四类服务；
- 登录 `admin/macro123`，验证前端首页看板与接口连通（部署验证截图：后台首页）。

**关键问题与解决**：

| 问题 | 根因 | 解决 |
|---|---|---|
| 后端启动失败 `Public Key Retrieval is not allowed` | MySQL 重启后 caching_sha2_password 认证缓存清空，JDBC 首次连接需公钥检索 | 将 `mall`@`localhost` 认证改为 `mysql_native_password` 并 `FLUSH PRIVILEGES`（一劳永逸） |
| 重新打包后 BouncyCastle 签名问题 | 打包替换了 JDK 加密 provider | 按《本地部署说明.md》执行 bcprov 签名修复 |

| 模块 | 前端路由 | 主要功能页 | 实测数据基线 |

## 4. 缺陷管理

### 4.1 BUG-001 商品列表页前端路由渲染异常

| 项 | 内容 |
|---|---|
| 缺陷编号 | BUG-001 |
| 严重程度 | 中（功能不可用但无数据损坏） |
| 复现步骤 | 登录后台 → 点击左侧菜单"商品列表"，或直接访问 `#/pms/product` → 页面渲染为"添加商品"（或"商品分类"）页 |
| 预期结果 | 展示商品列表（筛选条件 + 20 条商品） |
| 实际结果 | 页面组件与路由未正确对应，渲染异常 |
| 交叉验证 | 后端 `GET /product/list` 返回 200 与 20 条数据，**问题定位在前端 vue-router 动态路由匹配层** |
| 影响范围 | 商品列表入口不可用；UI 自动化用例对该页暂避让 |
| 关联用例 | CASE_PRODUCT_009（缺陷复现用例） |

### 4.2 缺陷分析方法论沉淀

- **三层定位法**：前端现象 → 后端接口交叉验证 → 定位故障层（本次锁定前端路由层，排除后端与数据层）；
- **缺陷用例化**：将缺陷复现步骤固化为自动化用例（CASE_PRODUCT_009），防止回归遗漏。

## 5. 亮点实战：性能瓶颈定位（线程栈 → 根因）

> 本节为本次项目最具方法论价值的部分：**面对"并发下响应时间劣化 600 倍"的性能问题，如何用证据链定位到代码层根因**。

### 5.1 问题现象

商品列表接口 100 并发持续负载下：平均响应由单发 44~70ms 恶化至 **1.3~6s**（劣化 20~100 倍），TPS 仅 25~65，未达目标 100。

### 5.2 排查过程（假设 → 验证 → 排除）

| # | 假设 | 验证手段 | 结论 |
|---|---|---|---|
| 1 | 负载模型问题（ramp 窗口低估） | 改持续负载模型复测 | ❌ 排除：真实并发下依然慢 |
| 2 | MySQL 连接池过小 | 外部配置覆盖 20→200 | ❌ 排除：无改善 |
| 3 | 日志 IO（SQL DEBUG + 全量 JSON 日志） | 日志级别降级/关闭 WebLogAspect | ❌ 排除：无改善 |
| 4 | Lettuce 连接池 | 外部注入 commons-pool2 + pool 配置 | ❌ 排除：实测更差，回退 |
| 5 | **Redis 共享连接全局锁** | **压测中 `jstack` 采样线程栈** | ✅ **确认** |

### 5.3 证据链

**证据 1：jstack 线程栈（决定性证据）**。压测期间 100 个 http-nio 工作线程中 **97~100 个全部阻塞**于同一位置：

```
java.util.concurrent.locks.ReentrantLock.lock
org.springframework.data.redis.connection.lettuce.LettuceConnectionFactory.doInLock
org.springframework.data.redis.connection.lettuce.LettuceConnectionFactory.getOrCreateSharedConnection
org.springframework.data.redis.core.RedisTemplate.execute
```

即 spring-data-redis + Lettuce **共享连接（shareNativeConnection 默认 true）的全局 ReentrantLock**：JWT 认证过滤器每请求执行 1~2 次 Redis 操作，100 并发下全部串行抢同一把锁 → CPU 近 0% 但延迟飙升（锁等待不耗 CPU）。

**证据 2：对照实验**。免认证接口 `/actuator/health` 100 并发 TPS **295**；认证商品接口 `/product/list` 100 并发 TPS **89**——差异约 3 倍，全部来自 Redis 串行化。

**证据 3：CPU 采样**。压测期间 java 进程 CPU 0~1%、mysqld 0%，排除计算/DB 瓶颈。

### 5.4 优化结果与建议

| 配置 | 商品 TPS | avg | P95 |
|---|---|---|---|
| 默认基线 | 37~51 | 4~6 s | ~7 s |
| **连接池 200 + 日志降级（保留固化）** | **89.32** | **973 ms** | **1643 ms** |
| Lettuce pool（已回退） | 14 | 6.4 s | ~9 s |

**已固化的配置级优化**（无需重新打包，外部覆盖）：Druid 连接池 20→200、日志级别降级，通过 `mall-overrides.yml` + `--spring.config.additional-location` 加载。

**代码层建议（移交开发）**：换用 Jedis 客户端或正确接线 Lettuce 连接池；JWT 过滤器用户/资源信息改本地短 TTL 缓存；商品列表加 Redis 缓存。

**方法论总结**：性能问题定位 = 现象量化 → 控制变量实验 → 线程栈/资源证据 → 根因锁定 → 可复现的优化与建议。
