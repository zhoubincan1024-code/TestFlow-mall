## 1. 文档目的

为 **TestFlow——Mall 电商系统自动化测试项目** 明确第一阶段的测试范围、测试类型、测试环境、测试策略与风险，作为后续编写功能测试用例、搭建接口/UI 自动化框架、执行性能测试的统一依据。

本计划为 **V1.0 第一版**，后续随项目推进（新增前台商城、扩展测试类型）持续修订。

---

## 2. 项目背景

- **被测系统**：开源电商系统 macrozheng/mall（官方 GitHub 仓库，master 分支）
- **测试定位**：2026 年软件测试校招作品集项目，覆盖功能测试、接口自动化、UI 自动化、数据库验证、性能测试、测试报告与 CI 全链路
- **技术栈（锁定）**：Python + Pytest + Requests + Selenium + PyMySQL + JMeter + Allure + GitHub Actions
- **版本锁定**：mall master（Spring Boot 3.5+ / JDK 17）；前端 mall-admin-web（Vue 3 + Element Plus）

> 本项目为个人测试学习与作品集项目，测试代码与被测系统分离管理（测试仓库 TestFlow-mall，被测源码 mall / mall-admin-web 仅作本地被测环境）。

---

## 3. 测试目标

1. 验证 Mall 电商后台管理系统 5 大模块（首页看板、商品、订单、营销、权限）的核心功能符合预期。
2. 建立可复用的**接口自动化测试框架**（Pytest + Requests），覆盖登录、商品、订单等核心接口 20+ 条。
3. 建立基于 **Page Object Model 的 UI 自动化**（Selenium），覆盖登录、商品管理、订单管理等核心业务链路。
4. 通过 **JMeter** 对登录、商品列表查询、混合业务场景进行性能摸底，输出 TPS / P95 / 错误率。
5. 通过 **数据库层验证**（PyMySQL）校验接口与数据一致性。
6. 使用 **Allure** 统一生成测试报告，并通过 **GitHub Actions** 实现接口测试自动回归。**【M8 已完成】**：Allure 已接入接口框架（41 条用例按模块自动分层，`reports/allure-report`），GitHub Actions workflow（`.github/workflows/api-ci.yml`）已落地：MySQL/Redis 容器化 + 锁定 commit 被测系统 + 全自动回归 + Allure 报告 artifact。
7. 在项目过程中沉淀一份包含缺陷分析（含已发现的 BUG-001）的完整测试资产，作为简历亮点。

## 6. 测试类型与策略

| 测试类型 | 策略说明 | 工具 | 优先级 |
|---|---|---|---|
| 功能测试 | 基于《功能模块分析》逐模块手工+用例化验证，产出约 100 条用例（Excel 管理） | Excel + 后台实测 | P0 |
| 接口测试 | 登录获取 token → 参数化用例 → Token 接口关联 → 数据库校验；20+ 条用例 | Python + Requests + Pytest | P0 |
| UI 自动化测试 | Page Object Model 封装页面对象，显式等待、失败自动截图；覆盖登录、商品搜索、新增商品、订单发货等核心链路 | Selenium + Pytest | P1 |
| 数据库测试 | 接口结果 ↔ 表数据一致性（pms_product、oms_order、ums_admin 等）；造数与数据清理 | PyMySQL | P1 |
| 性能测试 | 登录（并发 50）、商品列表查询（并发 100）、混合场景（8:2），指标：TPS、P95、错误率 | JMeter | P1 |
| 权限/安全基础 | 未登录访问受保护接口返回 401；角色越权（商品管理员访问订单接口）验证 | Requests | P1 |
| 测试报告 | Allure 报告 + JMeter HTML 报告统一归档 | Allure | P2 |
| 持续集成 | 接口测试接入 GitHub Actions 自动回归（提交触发） | GitHub Actions | P2 |

### 测试优先级定义

- **P0**：核心主链路（登录、商品查询、订单查询、权限拦截），必须先行覆盖。
- **P1**：重要业务功能（新增商品、上下架、推荐位、退货处理、性能摸底）。
- **P2**：增强项（报告美化、CI 集成、全量回归）。

## 8. 测试数据策略

1. **基线数据**：沿用官方 SQL 种子数据（`mall\document\sql\mall.sql`，已导入），商品 20、订单 48、用户 8 等。
2. **造数**：营销模块（优惠券/秒杀）数据已过期，执行营销相关测试前通过后台"添加"或 SQL 构造**有效期内**的新数据；订单状态流转数据（待付款→已发货等）用 SQL/接口构造。
3. **数据隔离**：数据库层验证与功能测试共用 `mall` 库，涉及**新增/修改/删除**的用例执行后回滚或清理（记录造数脚本到 `test-data/`）。
4. **账号数据**：测试账号 admin/test 为固定数据，不删除；批量测试使用临时账号（如 test_auto001 系列），用后清理。

## 10. 通过 / 退出准则

**用例通过准则（每个测试项）**：
- 功能用例：预期结果与实际结果一致；缺陷均登记并分类。
- 接口用例：响应 code=200、核心字段校验通过；鉴权用例返回 401 符合预期。
- UI 用例：断言成功、截图归档；脚本 100% 通过视为该轮回归通过（存在已知缺陷的用例标注 BUG 编号不算失败）。
- 性能用例：参考指标——登录 TPS ≥ 50、商品列表 TPS ≥ 100、P95 < 500ms、错误率 < 0.5%（以本机实际性能摸底后修正基准）。

**阶段退出准则**：
- 当前阶段用例执行率 100%，通过率 ≥ 95%（缺陷已登记未修复的除外）。
- 缺陷（Bug）均有编号、步骤、预期/实际、严重级别，且 BUG-001 等已知问题有分析记录。
- 测试报告（Allure/JMeter HTML）可查看并归档。

## 11. 风险分析与应对

| 编号 | 风险 | 影响 | 应对措施 |
|---|---|---|---|
| R1（BUG-001） | **商品列表页（#/pms/product）前端路由渲染异常**：点击菜单显示"添加商品/商品分类"内容，无法查看商品列表；后端 /product/list 接口正常（20 条） | 商品模块 UI 测试基线受阻 | ① 定位前端 vue-router 动态路由匹配问题（已有复现步骤与接口/数据交叉证据）② UI 自动化商品列表用例暂以接口 + 其他可用页面代替，并在缺陷库跟踪 |
| R2 | 营销数据（优惠券/秒杀）已过期（2022-2023 年数据） | 营销模块"上线/领取/核销"场景无法直接测试 | 测试前造有效期内新数据（后台添加/SQL） |
| R3 | 首页看板统计数值（今日订单 200 等）与明细数据口径不一致（示例聚合值） | 数据一致性断言易误报 | 明确断言口径：看板校验只断言展示结构，数据一致性校验走接口+DB |
| R4 | Python 3.14 较新，Pytest/Selenium 相关依赖兼容性待验证 | 自动化环境搭建受阻 | 搭建时先做依赖兼容性冒烟；必要时使用虚拟环境指定兼容版本 |
| R5 | 重新 `mvn clean install` 构建后端后需重做 BouncyCastle 签名修复（JDK17 JCE 校验），否则登录接口报错 | 环境重建后服务不可用 | 修复方法与修复包已存档（`C:\Users\zhoub\tools\bcprov-check\bcprov-fixed.jar`），记录在《本地部署说明.md》 |
| R6 | UI 自动化脚本对前端页面元素（class/文案）敏感，前端改动导致用例失效 | 回归成本高 | POM 封装 + 稳定定位策略（优先 id/自定义属性）+ 失败截图定位 |
| R7 | GitHub Actions 与本地环境差异（无法跑 Selenium GUI、需独立启动服务） | CI 回归覆盖不全 | CI 先接接口测试（自带启动脚本或远端可访问环境）；UI 测试本地执行并归档报告 |
| R8 | 数据库测试误操作污染共享测试库 | 后续用例数据失真 | 增删改用例自带数据清理；造数脚本入 test-data/ 并登记 |
