| 项目 | 内容 |
|---|---|
| 被测系统 | mall 电商后台（Spring Boot 3.x + JDK 17 + MySQL 8 + Redis） |
| 测试工具 | Apache JMeter 5.6.3（非 GUI 模式） |
| 测试时间 | 2026-09-09 |
| 测试环境 | Windows 11 本机（32 核），后端/数据库/前端同机部署 |
| 执行人 | 软件测试实习作品集项目 |

---

## 1. 测试概述

### 1.1 测试目标（对照《测试计划》第 9 章性能测试目标）

| 指标 | 目标值 |
|---|---|
| 登录接口 TPS | ≥ 50 |
| 商品列表 TPS | ≥ 100 |
| 响应时间 P95 | < 500 ms |
| 错误率 | < 0.5% |

### 1.2 测试范围

- 接口：`POST /admin/login`（登录）、`GET /product/list`（商品列表）
- 场景：
  1. **登录并发 50**：50 并发用户同时登录，每用户循环 10 次
  2. **商品列表并发 100**：100 并发用户，每用户先登录 1 次获取 token，再循环 5 次查询商品列表
  3. **混合 8:2**：80 个登录线程 + 20 个商品线程，模拟混合业务流量

### 1.3 业务流与数据关联

- 登录返回 JWT token（`$.data.token`），经 JSON 提取器存入 `login_token` 变量；
- 商品列表请求携带 `Authorization: Bearer ${login_token}` 请求头；
- 断言：响应体包含 `"code":200`（mall 业务码，HTTP 200 不代表业务成功，必须断言业务码）。

## 2. 测试执行过程

### 2.1 环境准备

| 项 | 说明 |
|---|---|
| JMeter 安装 | 5.6.3 自阿里云镜像下载，解压至 `C:\Users\zhoub\tools\apache-jmeter-5.6.3` |
| JAVA_HOME | 需显式指向 JDK 17（`C:\Program Files\Java\jdk-17`） |
| 服务就绪 | 8080（后端）/ 6379（Redis）/ 3306（MySQL）全部监听后执行 |

### 2.2 环境修复（执行前）

1. **MySQL 认证异常（Public Key Retrieval is not allowed）**：MySQL 服务重启后，`mall` 账号的 caching_sha2_password 缓存清空，JDBC 连接报错导致后端启动失败。修复：将 `mall`@`localhost` 认证方式改为 `mysql_native_password` 并 `FLUSH PRIVILEGES`。
2. **JMX 加载失败（ClassCastException）**：HeaderManager 不能放在 sampler 元素内部，必须作为 sampler 的子节点放入其 `<hashTree>` 层级，且每个子节点后跟独立的空 `<hashTree/>`。

### 2.3 执行命令

```powershell
$env:JAVA_HOME = "C:\Program Files\Java\jdk-17"
& "C:\Users\zhoub\tools\apache-jmeter-5.6.3\bin\jmeter.bat" -n -t performance-test\mall_perf.jmx -l performance-test\results.jtl -e -o performance-test\report -j C:\Users\zhoub\tools\jmeter_run.log
```

### 2.4 测试过程（三轮迭代）

| 轮次 | 变更 | 结果 |
|---|---|---|
| 第 1 轮 | 生成 JMX 含 HeaderManager 位置错误 | JMX 加载失败（ClassCastException），修复节点层级 |
| 第 2 轮 | 登录请求漏配 Content-Type、商品请求漏配 Authorization 头 | 登录全部 415，错误率 58.02%；修复请求头接线 |
| 第 3 轮 | 登录成功（错误率 0），但循环控制器嵌套导致商品样本量偏小 | 简化结构：登录用"仅一次控制器" |
| 第 4 轮（最终） | 结构定稿 | **2020 样本，错误率 0%**，指标见下 |
| 第 5 轮（优化复测） | 商品列表 100 并发持续负载 + 连接池/日志优化 | 商品 TPS 25.52 → **89.32**，详见第 7 章 |

### 3.2 目标达成情况

| 指标 | 目标 | 实测 | 结果 |
|---|---|---|---|
| 登录 TPS | ≥ 50 | 场景1：48.42 / 混合组：78.44 | ⚠️ 场景1 差 3.2%（含 ramp 启动开销），混合组达标 |

### 3.3 关键结论

1. **稳定性优秀**：2020 个请求 0 错误。
2. **响应时间优秀**：登录 P95 77ms（目标 500ms 的 15%）、商品 P95 8ms。
3. **登录吞吐接近目标**：50 并发下稳态 48.42 TPS；80 并发混合组可达 78.44 TPS。
4. **商品接口吞吐未达 100 TPS**：100 并发下实测 25.52 TPS（口径低估，见第 7 章复测）。

## 4. 性能瓶颈分析（商品列表 TPS 未达标）

| 因素 | 分析 |
|---|---|
| 接口链路 | `GET /product/list` 需经 JWT 认证过滤器（每次校验 token + 查 Redis/内存）+ MyBatis 分页查询 |
| 数据量 | 商品表 38 条（含逻辑删除过滤），单次查询开销小但认证开销占比高 |
| 应用配置 | 默认连接池/线程池参数未针对并发调优 |
| 环境 | 单机部署（JMeter 与被测应用同机），JMeter 自身 100 线程与后端抢占资源 |
| 吞吐口径 | 场景 ramp 20s 计入 TPS 计算窗口，拉低平均吞吐 |

---

## 5. 测试风险与说明

1. **单机压测**：压测客户端与被测服务同机，结果偏保守，仅作相对性能基线。
2. **并发量口径**：TPS 为 JMeter 官方统计口径（含 ramp 窗口）。
3. **登录场景循环登录**：每次循环重新登录获取新 token，未发现 session/token 冲突。
4. **混合场景比例**：80 登录 : 20 商品（8:2），与实际业务占比对齐。

## 7. 商品列表 TPS 优化复测（2026-09-09 补充）

### 7.1 复测背景

原报告中商品列表 TPS 25.52 的口径存在低估：场景 ramp 20s 拉长统计窗口、每线程仅 5 次请求。改用持续负载模型复测：100 线程 × ramp 5s × 每线程循环 20 次（2000 样本），并同步实施配置级优化。

### 7.2 优化措施与实测结果（100 并发持续负载）

| 轮次 | 配置 | 商品 TPS | avg | P95 | 错误率 |
|---|---|---|---|---|---|
| 优化前基线 | 默认配置（连接池 20 + debug 日志） | 37~51 | 4~6 s | ~7 s | 0% |
| + 连接池 20→200 | 仅 druid max-active 调大 | ~37 | ~5.7 s | ~7 s | 0% |
| + 日志降级 | 连接池 200 + SQL/WebLogAspect 日志关闭 | 45~65 | 1.3~2.0 s | 2.1~2.5 s | 0% |
| + Lettuce pool | 外部注入 commons-pool2 + pool 100 | 14 | 6.4 s | ~9 s | 0% ❌ 更差，已回退 |
| **最终（保留）** | **连接池 200 + 日志降级** | **89.32** | **973 ms** | **1643 ms** | **0%** |

**结论：优化复测较默认基线提升明显**——商品 TPS 由 37~51 提升至 **89.32**（+75%~140%），平均响应由 4~6s 降至 **973ms**，但 **TPS≥100、P95<500ms 目标仍未达成**（达成率：TPS 89%）。

### 7.3 瓶颈定位（线程栈证据）

压测期间对后端执行 `jstack` 采样，100 个 http-nio 工作线程中 **97~100 个全部阻塞于**：

```
org.springframework.data.redis.connection.lettuce.LettuceConnectionFactory.doInLock
org.springframework.data.redis.connection.lettuce.LettuceConnectionFactory.getOrCreateSharedConnection
org.springframework.data.redis.core.RedisTemplate.execute
```

即 **spring-data-redis + Lettuce 共享连接（shareNativeConnection 默认 true）的全局 ReentrantLock**：每次 Redis 操作（mall 的 JWT 过滤器每个请求执行 1~2 次 Redis 读/写）都要竞争同一把锁，100 并发下所有请求串行排队等待。

对照实验佐证：
- 免认证接口 `/actuator/health`（不走 JWT/Redis）：100 并发 TPS **295**、avg 312ms
- 认证商品接口 `/product/list`（走 JWT/Redis）：100 并发 TPS **89**、avg 973ms
- 差异 ~3 倍，全部来自 JWT 过滤器中的 Redis 串行化

### 7.4 结论与代码层优化建议

1. **已证实的配置级优化**：Druid 连接池 20→200 + 日志级别降级，已固化为 `mall-overrides.yml`（随 `--spring.config.additional-location` 加载，无需重新打包）。
2. **剩余瓶颈为代码层**（测试侧无法绕开）：
   - **换用 Jedis 客户端**（Jedis 连接池并发友好）或给 Lettuce 正确配置连接池；
   - **降低 JWT 过滤器 Redis 依赖**：用户信息/资源列表改为本地缓存或短 TTL 内存缓存；
   - 为商品列表增加 Redis 缓存，直接减少 DB 与认证链路上的重复开销。
3. 单机压测会进一步放大客户端竞争，建议后续在独立压测机复测。
